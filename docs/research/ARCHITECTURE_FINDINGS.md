## 1. 关键技术模式发现

### 发现 1：声明式步骤与变量引用的流水线模型（星月写作）
- **问题背景**：长篇小说不能靠单次对话生成，必须拆为“脑洞 -> 设定 -> 大纲 -> 细纲 -> 正文”。
- **架构解法**：通过 `Workflow` 抽象，每个 Step 拥有唯一标识 `step_id`，下游 Step 的 Prompt 模板中使用 `{{step_id.output}}` 引用上游变量。
- **人机协同关键**：支持“分步执行”，每步生成后允许作者在卡片内【编辑输出结果】。下游 Step 消费的是**作者人工修正后的内容**，从而在流水线中构筑了强大的质量防波堤。

### 发现 2：因果义务链与单世界主视角投影（novel-studio）
- **问题背景**：AI 创作长篇时极易发生“NPC 静止等待主角触发”、“章节之间因果悬浮、生硬跳转”。
- **架构解法**：
  - 上一章末尾生成的 Consequences（后果事件），强制作为下一章 Causal Beats 的 Causes（原因前置）消费；
  - 世界推演与正文视角解耦：模拟层推演世界各势力独立动作，渲染层仅向作家 Agent 注入主角感官可及的因果事实。

### 发现 3：作者文风档案采访与约束（Novel Engine）
- **问题背景**：各模型生成的小说普遍存在 AI 腔调（词汇重复、假大空感叹、缺乏市井烟火气或特定文风）。
- **架构解法**：建立 `VoiceProfile`，通过采访问答或范文解析提取句子结构、比喻习惯、节奏倾向，并作为 System Prompt 硬约束层级注入写作模型。

### 发现 4：审稿仲裁与错误反馈闭环（novelforge 参考项目）
- **问题背景**：AI 审稿报告如果不与正文修改联动，就成了无用的“废纸看板”。
- **架构解法**：审稿 Finding 支持【一键确认采纳】（生成修改建议并替换到正文草稿）与【标记误报/忽略】（记录到忽略列表，避免后续重复报警）。

## 2. 对 NovelForge AI 演进的技术架构指导

1. **绝对坚持本地优先与数据主权**：
   - 数据完全保留在 SQLite，利用 WAL 模式与 FTS5 虚拟表，性能大幅优于云端 SaaS；
2. **充分发挥 Docking 工作台优势**：
   - 将工作流看板、专项工具箱、提示词中心无缝注册为 Docking 面板，用户可在分屏中同时查看“工作流推进”、“正文编辑”、“角色关系图谱”与“长期记忆检索”；
3. **分层增强，拒绝大重构**：
   - 复用现有的 `SerializationJob`、`Database`、`ModelGateway` 与 `MemoryEngine` 底座，在其上构建高内聚的模块层。
